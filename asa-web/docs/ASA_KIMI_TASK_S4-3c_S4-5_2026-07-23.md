## 背景一句话

#154 第 7 轮实测暴露两个根因：① X-SaaS 查询被多关键词嵌套拼接（`selected_query` 见 `workflow_bcab82502825` 的 sourcing-funnel），8 组全 0 且归因只报 `unknown`；② 猎聘排重率 119/120=99%，池已枯竭但系统无信号、无扩池动作，迭代只会降目标。N1-N6 是对应修复。

## 执行顺序（严格按序，每项独立 commit、独立过守卫）

### S4-3c-1：N2 0 归因升级（最小改动先行）
- `classify_zero_result`（`scripts/a_system_agent/capability_runtime.py`）新增两类：
  - `query_build_error`：查询含异常拼接模式（如"关键字："嵌套、单查询 ≥2 个公司名、空查询）
  - `pool_saturated`：召回正常但 `dedupe_rate > 90%`
- 契约测试：用 `workflow_bcab82502825` 的 X-SaaS 真实查询形态做断言（嵌套拼接 → `query_build_error`）。
- 前端归因中文文案同步进 `statusMapping` 体系（不新增本地映射）。

### S4-3c-2：N1 渠道查询方言层
- 在策略输出与渠道 runner 之间加逐渠道 `query_builder`：
  - 猎聘：维持现有组合查询；
  - X-SaaS：拆分执行——公司词独立查询、职能/技术词独立查询，逐条跑完合并去重；单查询不得含 ≥2 个公司名。
- 契约测试：输入 `knowledge_base/seed_silan_tme_v1.json` 的关键词组，断言 X-SaaS 输出符合方言规则。
- 落地后用活跃岗位跑一轮真实寻访验证：X-SaaS `recall_count > 0` 或归因明确为 `no_results`（仍是 0 也不许报 `unknown`）。

### S4-3c-3：N3 池枯竭信号 + 扩池决策树
- 复盘器（S4-3 已建）增加：`dedupe_rate > 80%` 触发 `pool_saturated` 信号，并按序输出扩池决策树（换关键词组 → 扩 T2/T3 池 → 放宽条件 → 渠道再平衡 → 建议转 Mapping/与客户校准），写入 `strategy_review` artifact。
- 前端"调整条件再搜"把决策树渲染为可选步骤（可逐项采纳），不接空白输入框。
- 验收：构造排重率 >80% 的测试工作流产出有序决策树；真实工作流触发时数据留痕。

### S4-3c-4：N6 策略全要素消费检查（可与前项并行）

### S4-5：N4 渠道效能学习 + N5 评估校准暴露（S4-4 之后）
