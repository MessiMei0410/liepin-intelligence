## 本期范围（三件事）

### ① 任务卡视图（PRD §4 原范围）

- 工作流详情页：扩池决策树末端"发起 Mapping 直挖"按钮 → 调现有 POST 接口创建任务并打开任务卡视图。
- 任务卡视图（工作流详情内新 tab 即可，不另起页面）：左侧目标团队树（公司→团队→置信度），右侧人选卡（当前职务/来源链接直接可点/推荐理由/状态）。
- 顾问逐人操作：**确认 / 删除**，确认后进入"待接触"队列；`consultant_note` 可编辑。
- 状态机七态：待确认 pending → 已确认 confirmed → 已接触 contacted → 已回复 replied → 已入库 intaken；另两态：搁置 parked / 淘汰 rejected。状态变更写库走后端 PATCH（幂等 + 审计，复用现有写入模式），已接触/已回复由顾问手动点选，Copilot 短指令可后续再接。
- 入库：仅对 confirmed 人选开放"入库"动作，走**现有** preflight/commit 候选人动作链路，**不写第二条 job_candidates**，遮罩名合并规则照旧。
- stats 区展示线索有效率（确认数/采集数）与失败记账（failures 已在 schema 里，失败原因要人话展示，如"官网有反爬保护，没抓到"）。

### ② 逐人破冰素材生成（本期新增，核心增量）

- 对每位 confirmed 人选，基于其 `source_urls` 的线索内容（论文标题/专利方向/职务/所在团队）自动生成**开场白要点**，存入 candidate 的 `icebreaker` 字段：
  ```json
  "icebreaker": {
    "hooks": ["看到您在多相控制器方向的论文……", "MPS TME 团队到这个客户是平移还是上升……"],
    "angle": "技术共鸣 | 职业发展 | 地域 | 客户平台",
    "generated_at": "...", "source_ref": "用了哪条线索"
  }
  ```
- 生成时机：人选被"确认"时自动生成；人选卡上提供"重新生成"按钮。
- 质量要求：必须引用该人选的真实线索（论文题/专利词/团队名），**禁止泛泛模板**（"看您背景很优秀"这种一律不合格）；每条 hook 是顾问可直接念出口的口语句子，不是书面摘要。
- 话术红线继承 restricted 层：不得出现费率、不得代顾问承诺、不得自动发送——素材只在卡上展示，发送动作永远由顾问本人执行。

### ③ 文案

- 全部新增 UI 文案遵循 UX-1 原则：业务语言。参考译法：icebreaker → 「开场白要点」；confidence → 「把握大/一般/偏小」；stats → 「这份名单的效果」。

## 红线（写死）

- 不自动触达、不自动发消息；破冰素材只展示不发送。
- 入库不开旁路：preflight/commit/幂等/审计全复用。
- 禁挖名单、遮罩名合并规则不放松。
- 人选删除是软删（状态 rejected），不物理删 artifact 数据。

## 验收标准

1. 用 #154 已有 artifact（或重新生成一份）在 App 里走完整流程：打开任务卡 → 左侧团队树正确渲染 17 团队 → 确认 2 人 → 每人自动生成破冰素材且引用真实线索 → 改状态到"已接触" → 刷新后状态持久。
2. 入库动作走通 preflight/commit，job_candidates 不出现重复条目（回归断言）。
3. 契约测试：icebreaker 为空/模板化文案（如不含该人选任何线索关键词）判不合格；无 source_urls 人选依旧无法入库。
4. e2e functional 覆盖任务卡主流程（确认/状态变更/入库按钮存在性）。

## 门禁层级

- L1 `npm run ci:fast` 必过；

- 真实验证：验收 1 在正式库走一遍（只读 + 少量状态写入，允许）。
