## 0. 目标与定位

**解决的问题**：简历库寻访（猎聘/X-SaaS）对高端、稀缺、被动型人选天然失效——#154 七轮枯竭（排重率 99%）证明池子会干。资深顾问的终极打法是按组织架构 Mapping 直挖：锁定目标公司的目标团队，逐人定点突破。

**一句话目标**：当扩池决策树走到"本地池+渠道池已尽"，或顾问手动发起时，ASA 能产出一份**可执行的直挖任务卡**——目标团队、目标人名单、线索来源、行动建议、状态跟踪——并把结果回流知识库。

**红线（继承战略 PRD，写死）**：
- Mapping 名单来自**公开信息只读采集**（官网/公众号/招聘 JD/专利论文/脉脉公开页），不破解、不绕过登录墙后的非公开数据。
- **绝不自动触达**。名单是给人看的，行动（私信/微信/电话）全部由顾问本人执行；系统只提供任务卡、话术素材和状态跟踪。
- 脉脉渠道：浏览器登录态只读（WebBridge），不自动发消息、不批量翻页。

## 1. 业务流程

```
触发（N3 决策树末端 / 顾问手动"发起 Mapping"）
 → ① 目标团队定位：策略 v2 的 T1/T2 公司池 → 每家公司定位目标团队
     （产品线/部门/地域），证据来源标注
 → ② 线索采集（只读）：官网团队页、公众号、招聘 JD、专利/论文作者、
     脉脉公开资料 → 候选目标人清单
 → ③ 名单生成：姓名/当前职务/所在团队/线索来源 URL/置信度/推荐理由
     → 顾问逐人确认（删除/保留/调整优先级）
 → ④ 直挖任务卡：按人一张卡——背景摘要、破冰切入点、建议触点、
     状态机（待接触/已接触/已回复/已入库/搁置/淘汰）
 → ⑤ 结果回流：确认入库的人选走现有 preflight/commit + intake；
     团队结构沉淀为公司图谱"团队层"；名单质量回写 Mapping 评测
```

## 2. 数据模型

新 artifact 类型 `mapping_task`（复用 agent_artifacts 体系，不建新表）：

```json
{
  "schema_version": "mapping_v1",
  "trigger": "decision_tree_exhausted | manual",
  "job_id": 154,
  "strategy_ref": "strategy_v2 artifact id",
  "target_teams": [
    {"company": "杰华特", "team": "计算电源产品线 TME/FAE 团队", "location": "杭州",
     "evidence": [{"type": "官网|公众号|招聘JD|脉脉|图谱", "ref": "url 或图谱条目", "as_of": "date"}],
     "confidence": "high|medium|low"}
  ],
  "candidates": [
    {"name": "张某", "current_role": "Senior FAE", "team_ref": 0,
     "source_urls": ["..."], "confidence": "high|medium|low",
     "reason": "为什么打这个人（画像匹配点）",
     "status": "pending|confirmed|contacted|replied|intaken|parked|rejected",
     "consultant_note": ""}
  ],
  "stats": {"teams": 0, "candidates": 0, "confirmed": 0, "intaken": 0}
}
```

约束：`candidates[].name` 允许遮罩/姓氏+职务（Mapping 阶段常有半名）；确认入库时必须经现有遮罩名合并规则（交接文档 §6.4）。`source_urls` 必填——没有来源的人名不进名单（防编造，这是硬约束）。

## 3. 采集能力边界

| 来源 | 方式 | 边界 |
| --- | --- | --- |
| 官网/公众号/招聘 JD | 公开页面只读抓取（WebBridge 或现有抓取函数） | 全量允许 |
| 专利/论文 | 公开数据库（专利局/Scholar）按公司+技术词检索作者 | 只取姓名+单位+方向 |
| 脉脉 | WebBridge 浏览器登录态，只读公开资料 | 不自动发消息、不批量翻页、单团队采集限速 |
| 猎聘/X-SaaS | **不用于 Mapping 采集**（那是简历库逻辑，避免与 N1 方言层重复） | — |

采集结果统一走"线索 → 候选目标人"的两步，每条线索保留原始出处；采集失败/页面变动记入 task 的 stats，不静默。

## 4. 前端与交互

- 工作流详情页：扩池决策树末端"发起 Mapping 直挖"按钮 → 创建 `mapping_task` 并打开任务卡视图。
- 任务卡视图（新页面或工作流详情内 tab）：左侧目标团队树（公司→团队→人数），右侧人选卡（背景/来源/推荐理由/状态按钮）。顾问逐人"确认/删除"，确认后进"待接触"队列。
- 人选卡的"已接触/已回复"状态由顾问手动点选或 Copilot 短指令（复用现有一步写入模式）；确认入库走现有候选人动作链路（preflight/commit），**Mapping 名单不写第二条 job_candidates**（来源身份规则不变）。
- 视觉沿用工作台风格：信息密度优先，来源链接直接可见。

## 5. 知识回流

- 任务卡关闭/阶段性归档时，把确认过的团队结构（公司→团队→人数→关键角色）写入公司图谱的 `teams` 扩展层（图谱 JSON 只读原则的例外：由知识库维护流程写入，带 as_of 日期）。
- 名单质量指标进回放评测体系：线索有效率（确认数/采集数）、转化率（入库数/确认数）、与后续成单路径的对照。

## 6. 分期与验收

| 期 | 内容 | 验收 | 依赖 |

每期独立 commit、独立过 `npm run ci` + Core 测试 + A 系统回归守卫。

## 7. 硬性约束（汇总）

- 不自动触达、不自动发消息——Mapping 的全部对外动作由顾问本人执行。
- 人名必须有公开来源 URL，无来源不进名单；遮罩名合并不放松现有规则。
- restricted 层边界同 S4：禁挖名单照常生效（禁挖公司的人不进名单）；费率/话术红线不出现在任何对外输出。
- 脉脉采集限速、只读、登录态由顾问本人浏览器提供。
- 入库链路全部复用现有 preflight/commit/幂等/审计，Mapping 不开旁路。

## 8. 度量

- 池枯竭岗位的 Mapping 覆盖率（枯竭后发起 Mapping 的比例）
- 线索有效率、确认→入库转化率
- Mapping 来源人选的高分率 vs 简历库来源（验证"直挖质量更高"假设）
