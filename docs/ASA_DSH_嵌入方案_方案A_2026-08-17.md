# ASA 嵌入 DeepSeek Harness（方案 A）实施方案

> 状态：方案草案（待评审）
> 日期：2026-08-17
> 决策：用户选定方案 A —— 以 DeepSeek Harness (DSH) 作为 ASA 的唯一 Agent 大脑，逐步退役 Python 手写 Copilot 状态机。
> 前提：全程不破坏 preflight/commit、幂等、审批、审计、候选人状态不可倒退等业务安全规则；遵循仓库 PR + 三层 CI 门禁。

---

## 1. 背景与结论先行

ASA 现在已经在用 DeepSeek **模型**（`deepseek-v4-pro`，经 `scripts/a_system_agent/llm.py` 直连 DeepSeek 兼容 API），但 Agent **运行时**是一套 Python 手写状态机（`copilot_impl.py` / `copilot_handler.py` / `turn_decision.py` / `conversation_state.py` 等），能力上限受限于这套规则路由。

DeepSeek Harness (DSH) 是另一回事：一个 Node/TS 的通用 Agent 框架（npm `@deepseek-ai/dsh`，当前 `0.1.0-rc.6`，Cordis 插件体系）。它提供的正是 ASA 手写层没有的通用编排能力：

- 子代理 fan-out（`subagent` / `subagent_fork`，可并行核实/多视角）
- 跨轮目标持久化（`goal` / `goal-round-driver`）
- 工作流编排（`workflow` / `workflow-worker-thread`）
- skill 复用体系（`skill` / `skill-filesystem`）
- 会话压缩与 token 治理（`compaction-basic` / `token-meter`）
- MCP 客户端、模型选择、审批/权限堆栈（`user-approval` / `permission-presets`）

**核心判断**：DSH 的价值在"通用 Agent 运行时 + 编排 + 治理"，不在"更强的模型"。ASA 的业务安全规则落在 **ASA Core 服务端**（preflight/commit、幂等、审批、审计），不在 Copilot 聊天循环里。因此"用 DSH 替换 Copilot 循环"是可行的，前提是 DSH 的工具全部通过 ASA Core 的 HTTP API 动作，且把"意图护栏"重新表达进 DSH 的 persona / agent-instructions / skill / 审批钩子。

---

## 2. 终态架构（目标）

```
ASA.app (WKWebView)
  └─ React Agent Surface (src/agent/)
       └─ HTTP/SSE ──► DSH sidecar（常驻 Node，自定义 `asa` profile）
                          ├─ 通用工具：bash / fs / web / subagent / goal / workflow / skill / MCP
                          ├─ ASA 工具（自定义 plugin）：
                          │     asa.jobs / asa.candidates / asa.workflows / asa.dashboard
                          │     asa.approvals.decision / asa.candidate.preflight / asa.candidate.commit
                          │     asa.sourcing.*（后续）
                          └─ persona + agent-instructions + `asa` skill（承载业务护栏）
                               └─ 全部写动作 → ASA Core HTTP API
                                              └─ v3 SQLite（唯一事实源）
                                              └─ 审批/幂等/审计/状态机（不变）
```

过渡态：Python `a_system_agent` 的 Copilot 循环**先保留并继续服务**，DSH 以"只读影子 → 受控写入 → parity"逐级切流，最后再退役 `copilot_impl.py` 等。

## 3. 关键决策与约束

| 项 | 决策 |
| --- | --- |
| 嵌入形态 | 方案 A 终态；落地顺序按"影子→写入→parity→切流→退役"（见 §4） |
| DSH 版本 | `0.1.0-rc.6`，**锁定**，升级单独走 PR + 回归 |
| DSH 运行位置 | 常驻 Node sidecar（进程由 LaunchAgent 管理，同 `ai.hermes.liepin-workbench` 模式）；Phase 0 用 `dsh --profile headless` 一次性验证 |
| 模型 | 沿用 ASA 的 `deepseek-v4-pro`（DSH 默认是 `deepseek-v4-flash`，需在 `settings.yaml` 的 `llm-deepseek:` 段指定） |
| 密钥 | DSH 读 `$DSH_HOME/.credentials.yaml`（或 `DEEPSEEK_API_KEY` env）。现有 `~/.dsh/.credentials.yaml` 已可用；**不得**把 key 写进仓库/bundle/日志。ASA Core 侧 Keychain 读取不动 |
| 写动作安全 | DSH 工具只调 ASA Core 的 HTTP 动作接口：`candidate-actions/preflight` + `commit`（带 `Idempotency-Key`）、`approvals/{id}/decision`、`workflows/*`。**DSH 绝不自建数据库写入** |

| 测试 | 写动作测试用 **/tmp 数据库副本**（沿用现有 E2E global setup 做法），绝不动正式 v3 库 |
| 仓库流程 | 新代码走 `feature/dsh-*` 分支 + PR；改前端/Core/扩展不混同一 PR |

## 4. 分阶段计划

### Phase 0 — 只读冒烟（零自定义代码）
用 `dsh --profile headless "<只读任务>"` 验证：DSH 能 (a) 用 bash+curl 触达 ASA Core 只读接口 (b) 产出结构化中文汇报。
- 成功标准：一次 headless turn 正确读出 bootstrap/dashboard 关键数。
- 顺带验证点：**沙箱是否放行 localhost 网络**（若 curl 被沙箱拦，则 Phase 1 必须走自定义工具的自带 HTTP 通道，而非 bash+curl）。

### Phase 1 — 只读 ASA 工具（自定义 DSH plugin）
- 新建 npm 包 `@asa/dsh-asa-tools`（或仓库内 `dsh/asa-tools/`），用 `@deepseek-ai/dsh-tools` 的 `defineTool` + `@deepseek-ai/schemastery` 注册 typed 工具：
  - `asa.dashboard`、`asa.jobs`、`asa.candidates`、`asa.workflow`、`asa.audit_events`
- 每个工具内部用 `fetch` 调 `http://127.0.0.1:8765/api/v1/...`（只读），返回 JSON。
- 新增自定义 profile/preset `asa`（复制 `standard` preset 的 `agent.cordis.yml`，注入 asa 工具 + persona + agent-instructions + skill）。
- 成功标准：headless 下 `dsh --profile asa "读岗位#154漏斗和候选人"` 通过 typed 工具完成，不再依赖 curl。

### Phase 2 — 受控写工具（1 个，走完整安全链路）
- 实现 `asa.candidate.record_followup`（记录"已读未回复"等低风险事实）：
  - 前端先 `preflight` → DSH 工具返回待确认 → 用户确认 → `commit`（带 `Idempotency-Key`）→ 审计/事件/学习反馈 → 原地刷新。
- 回归：重复写幂等、已停止候选人不可重新推进、阶段不可倒退。
- 成功标准：与现有 Copilot 写路径行为一致，且全部审计/事件落库。

### Phase 3 — parity 验证
- 建立固定场景集（读岗位、读候选人、记录跟进、创建寻访计划、审批决策、停止保护等）。
- 对每个场景，同时跑"现有 Copilot"与"DSH"，对比结果与副作用（事件/审计/工作流状态）。
- 成功标准：写场景 100% 副作用一致；读场景语义等价；记录差异并评审。

### Phase 4 — 前端接入与切流
- 新增 `src/agent/` 的 DSH 传输层（或复用 `/api/v1/copilot/stream` 由 Core 转发到 sidecar），SSE 流式返回。
- 会话持久化由 DSH session 承担；`localStorage` 会话 id 映射到 DSH session id。
- 灰度：先影子对照展示，再提供"切换 DSH"开关。
- 成功标准：`?surface=copilot` 完整走 DSH，四主导航/候选人详情/工作流详情入口仍能显式附着上下文进入 Agent。

### Phase 5 — 退役 Python Copilot 循环
- 仅当 Phase 3/4 连续稳定通过后，才分文件退役 `copilot_impl.py` / `copilot_handler.py` / `turn_decision.py` 等。
- 保留 `service.py` / `service_copilot_bridge.py` / `service_candidate_actions.py` / `service_workflow_ops.py` 等 **Core 服务端**动作/审批/审计实现（它们是安全层，不是退役对象）。
- 每一步单独 PR + 回归。

## 5. 必须重新表达的意图护栏（从现有 Python 层迁移到 DSH）

这些规则目前硬编码在 `copilot_impl.py` 等，必须等价迁移到 DSH 的 persona/instructions/skill/审批钩子，缺一不可：

1. 询问句（"已读不回怎么办"）只回答不写入；祈使句才写。
2. 执行性回答必须有真实 `workflow_id`，否则不得声称"已开始寻访"。
3. 停止 = 淘汰/关闭；已停止候选人不得被推进；重复停止/推进返回冲突。
4. 阶段不可倒退（已联系不得降回待复核；已推荐/面试/Offer 记"已读未回复"只补事件）。
5. 来源身份：本地候选人用 v3 `candidates.id`；外部 ID 是证据不是主键；不得写成第二条 `job_candidates`。
6. 遮罩名合并需姓氏 + 公司 + 职位证据同时匹配，走只读预检 + 一次性确认。
7. 外部寻访必须一次性 R3 审批；搜索卡片摘要不得冒充完整简历；partial/failed 不得 intake。

迁移验收：逐条用固定用例回归（与 §4 Phase 3 场景集合并）。

## 6. 风险与回退

| 风险 | 缓解 / 回退 |
| --- | --- |
| DSH rc 接口变动 | 锁版本；升级单独 PR；sidecar 隔离，坏则回退上一版 |
| 沙箱网络限制阻 curl | Phase 0 即暴露；改自定义工具自带 fetch 通道（不依赖 bash 沙箱） |
| 护栏迁移遗漏 → 错误写库 | Phase 3 parity 逐条对照；写动作全部走 Core 服务端校验（服务端兜底） |
| 两套 Agent 并存期混淆 | 影子对照只读、明确标注；切流开关灰度 |
| 性能/延迟 | sidecar 常驻（非 per-turn 子进程）；Phase 0 先测 headless 冷启动开销 |

回退：任何阶段未达标，DSH 保持只读影子或停用，Python Copilot 原样继续服务。

## 11. Phase 3 首轮 parity 发现（2026-08-17，关键）

**同一问题**（"现在工作台有多少活跃岗位、多少候选人和多少待处理候选人？"）分别问现有 Copilot（`/api/v1/copilot/stream`）与 DSH（`asa_dashboard` 工具）：

| 维度 | 现有 Copilot | DSH（当前 CRUD 工具） |
| --- | --- | --- |
| 候选人总数 | 805 ✅ | 805 ✅ |
| 待处理 | 574 ✅（并拆 526 待复核 / 85 待确认 / 50 待核验） | 574 ✅（仅一个数） |
| 活跃岗位 | "9 个 P0 最急"（语义=最急） | "35 活跃"（语义=active_jobs 原值） |
| 领域情报 | 异常点、停滞岗位、过期评估、下一步建议 | 无 |

**结论**：
- **数值 parity 成立**（805/574 同源）。
- **领域情报 parity 不成立**：Copilot 的价值不在 CRUD 也不在模型，而在 Python `copilot_context` / `copilot_intent` / `copilot_evidence` / `copilot_tools` 这层**领域情报**（业务上下文、异常检测、优先级、主动建议）。这层**埋在 `/api/v1/copilot/stream` 单体 handler 内，没有独立端点**（已确认 app.py 无 context/suggestions 只读路由）。
- 因此**裸 A（DSH 只挂 CRUD 工具）会产出比现有 Copilot 更笨的回答**——这正是当初推荐 B 的原因。

**两条出路（需用户拍板）**：
1. **A 做对**：把 `copilot_context`/`copilot_intent`/`copilot_tools` 抽成独立只读端点（`/api/v1/copilot/context`、`/api/v1/copilot/suggestions` 等），作为 DSH 工具暴露 → DSH 当编排 + 会话 + 审批门控，Python 提供领域情报工具。工作量最大，但真·A。
2. **A 降级为 B**：DSH 的"领域工具"就是现有 `/api/v1/copilot/stream` 本身——DSH 做多步编排（子代理/goal/workflow）套在现有 Copilot 之上，领域情报继续留在 Python。风险最低，但"大脑"仍是 Python。

> **2026-08-17 用户拍板：走路 2。** 目标改为「DSH 编排层 + Python 领域情报」；`退役 Python Copilot`（原 Phase 5）取消，Python 保留为领域情报与安全层。

## 13. Phase 4 v0：DSH 桥接服务（2026-08-17 已跑通）

新增 `dsh/bridge/asa_dsh_bridge.py`：把 `dsh --profile asa` 包装成 HTTP Agent 接口，供 ASA Core/前端调用。

- `POST /turn {message, context?}` → spawn `dsh --profile asa "<message>"` → 返回 `{ok, answer}`。
- `GET /health` → `{ok, profile}`。
- 环境变量：`DSH_BIN` / `DSH_HOME` / `ASA_DSH_BRIDGE_PORT`(默认 8890) / `ASA_DSH_TURN_TIMEOUT`。

## 17. 常驻服务器（v1，2026-08-17）——会话记忆 + 摊销启动

新增 bundle `@asa/dsh-asa-server`（`dsh/asa-server/`，照 `dsh-headless` 的 one-shot runner 改造为 resident）与 profile `asa-server`（`dsh/asa-server-profile/`，bundles = `dsh-base` + `@asa/dsh-asa-server`）。

- `dsh --profile asa-server` 起 `node:http` 服务器（默认 `ASA_DSH_RESIDENT_PORT=8891`），**不 exit**（与 headless 的 `io.exit` 相反）。
- `POST /turn {message, session_id?}`：`agents.create/get(sessionId)` 复用 live agent（`agent.id === session.id`），`agent.followup` → `whenIdle` → 聚合 `assistant/message` 文本返回；同一 `session_id` 复用同一个 agent → **多轮记忆**。
- `GET /health` → `{ok, profile}`；CORS 本地放行。

**关键坑（实测）**：bundle 的 `package.json` 必须声明 `dsh.bundle.patch`（指向其 `cordis.patch.yml`），否则 boot 报 `profile bundle ... declares no dsh.bundle`。

**验证**：
- 首轮 `/turn`（无 session_id）→ `{"ok":true,"session_id":"asa-…","answer":"35"}`。
- 次轮同 `session_id` 问「刚才的答案是多少，别调工具」→ `answer:"35"`（**未再调工具，纯会话记忆**）——per-turn 桥接做不到的记忆，resident 做到了。
- 前端 `transport.ts` 的 DSH 开关改指 8891 并带 `session_id`。

**流式（v1.1，2026-08-17）**：已实现——订阅 agent 会话 `session/event` 火线（`agent.ctx.on("session/event")`），把 `assistant/chunk` 的 `text-delta` 实时转 SSE `text` 事件；轮结束聚合最终文本发 `done`。前端 `streamDshTurn` 改走 SSE 解析（复用 `parseAgentSse`）。

**实测 SSE 流**：`event: progress`（DSH 编排中…）→ `event: text`（`{"content":"35"}`，逐 token）→ `event: done`（`{"session_id":"asa-…","answer":"35","ok":true}`）。

**剩余边界**：并发同 session 请求未加锁（前端单轮串行即安全）；进程无优雅清理；CORS/鉴权待收紧。
